# 04: 发送端真实采集与硬件编码

**What to build:** 把切片 01 的合成画面换成**真实屏幕**：申请 MediaProjection 权限，用虚拟屏 + MediaCodec Surface 输入零拷贝硬编 H.264，编码输出按会话协商的参数推出去。同时落地本地录制与截图复用的编码出口。用户价值：这一刻起，投的是真屏幕。
**Blocked by:** 03（会话握手与能力协商）
**Status:** ready-for-agent

- [ ] `MediaProjection` 权限流程：请求、被拒绝、被撤销、每次会话重新确认（新版本 Android 行为）都有明确 UI 处理
- [ ] 虚拟屏创建，并按**屏幕物理分辨率**采集（`NativeCapture`），编码前才降采样
- [ ] 编码尺寸取一个**固定档位**（16 倍数对齐，如源屏的一半）并全程不变 —— 这是工单 15 零重配放大能成立的前提
- [ ] 编码输入链路上留出**可替换的取样阶段**：虚拟屏 → GL 纹理 → 缩放/裁剪 → 编码器输入 Surface；本切片只实现 `FullScreen`（整屏缩放到编码尺寸），为工单 15 的 ROI 裁剪预留位置 —— **不要把虚拟屏直连编码器**，否则高清放大只能靠重构实现
- [ ] 编码配置来自握手协商结果（分辨率、帧率、码率、GOP），编码档位按 `MediaCodecInfo` 能力回退
- [ ] `VideoSource` 的生产实现落地，假实现仍保留给测试使用（接缝没被破坏）
- [ ] 关键帧可按需触发（供后续关键帧请求使用），GOP 固定且可配置
- [ ] `MediaClock` 落地：采集 `nanoTime` 映射为 90kHz 媒体时间戳，帧时间戳连续且单调
- [ ] 编码输出支持可插拔的第二个消费者（供本地录制/截图接入），且额外消费者不影响网络推流的帧率（录制与截图的产品化体验在工单 13）
- [ ] 投屏期间前台服务 + 通知（含"停止投屏"动作），息屏与切后台不中断
- [ ] 编码器创建失败/机型不支持时给出可读错误并回退到更低档位，不崩溃
- [ ] instrumentation 冒烟：编码器能建立并吐出首个 I 帧
- [ ] 手工验收：接入一个临时的本地消费者（如 MediaMuxer 落盘）后，编码帧仍与操作一致，且投屏帧率无可感知下降
