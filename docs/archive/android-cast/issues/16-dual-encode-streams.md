# 16: 双编码流 —— 动态场景的零重配两全（备选）

**What to build:** 发送端并行跑两条编码流：**全屏流**（高分辨率档，供整屏观看）与 **ROI 流**（编码尺寸 = 当前取样矩形的 1:1 尺寸，供放大观看）；接收端按 `ViewTransform` 在两条流之间切换，**切换零重配、无需冻结**。这样在动态场景（视频 / 游戏）下也能同时拿到"全屏空间分辨率"与"放大原生细节"。这是工单 15「单流 + 冻结重配」的备选升级路。
**Blocked by:** 15（ROI 高清放大 —— 零重配取样放大 + 冻结时重配）
**Status:** ready-for-agent（**备选**：判据不满足时不执行）

> **执行判据（先看这个再动手）**：工单 15 交付后，若在动态场景（播放视频 / 玩游戏）下放大画面时小字可读性不达标，**且**冻结路径不可用（画面在动，冻结就失去意义），则执行本工单；否则不执行，只需把实测数据记录在案。

- [ ] 设备能力探测：通过 `MediaCodecList` 查清可并发建立的编码会话数与支持的分辨率档；探测失败或不足 2 路时自动降级回单流（工单 15 行为），并在 UI / 日志说明原因
- [ ] 发送端双流实现：全屏流与 ROI 流并行编码，**共享同一个采集源**（虚拟屏纹理），不重复采集、不重复 GPU 上行
- [ ] 非活动流降耗：当前未显示的流降帧率或仅维持关键帧，切换时立即请求关键帧；切换延迟有实测数据（目标 < 300ms）
- [ ] 接收端双解码器：同时接收两路并随 `ViewTransform` 无缝切换；切换过程不黑屏、不重建解码器
- [ ] 码率分配：两路总码率受同一预算约束（与切片 12 的 `BitratePolicy` 协同），活动流优先、非活动流降到最低
- [ ] 资源守护：长时间双流运行不耗尽编码器实例、不过热降频掉帧；具备退回单流 + 冻结重配的降级路径
- [ ] 协议扩展：`CapabilitySet` 增加"并发编码路数 / 是否支持多流"，握手时协商；对端不支持则自动走单流
- [ ] 纯逻辑单测：双流码率预算分配、活动流切换决策、能力协商失败时的降级路径（可控时钟推进）
- [ ] 实测数据记录：双流 vs 单流的功耗、发热、延迟、码率、清晰度对照表 —— 这是决定该方案去留的依据
- [ ] 手工验收：播放视频 / 玩游戏时放大画面，小字清晰且全程无卡顿；与工单 15 单流方案的实测数据并列对比
