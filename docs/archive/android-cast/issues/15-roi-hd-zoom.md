# 15: ROI 高清放大 —— 零重配取样放大 + 冻结时重配

**What to build:** 接收端放大画面时，**只改变发送端编码前的取样矩形**（GPU 采样），编码尺寸全程固定 —— 于是放大、平移、切换倍率全程零重配、零卡顿、解码端无感。当倍率超过「编码尺寸 ↔ 源像素 1:1」的档位（如 4× 以上）且用户要原生像素时，通过接收端「**冻结画面**」创造安全窗口，在冻结期间重配编码尺寸；**绝不在播放中重配**。用户价值：在平板上像看地图一样连续缩放手机屏幕，小字清楚，全程不卡。
**Blocked by:** 06（真机端到端屏幕镜像打通）、05（接收端硬件解码与渲染，提供 `ViewTransform` 交互）
**Status:** ready-for-agent

> 两条不可退让的原则：
> 1. **编码尺寸固定，取样矩形可变。** 改码率走 `setParameters`（零重配），改分辨率才需要重配 —— ROI 放大靠前者就够，不必付重配的代价。
> 2. **绝不在播放中重配编码器。** 重配只允许发生在「画面冻结」或「会话重建」时，且必须有状态机守卫与测试防止未来回归。

- [ ] 发送端编码尺寸取一个**固定档位**（16 倍数对齐，如源屏的一半），全程不随取样矩形变化；`FullScreen` 只是"取样矩形 = 整屏"的特例
- [ ] `FullScreen`（整屏缩放到编码尺寸）行为与切片 06 一致，改造不引入画质或延迟回归；虚拟屏仍按屏幕物理分辨率采集（`NativeCapture`）
- [ ] `RoiRequest`（走控制通道）定义与传输：归一化取样矩形 + 目标档位（`SameResolution` / `Native1to1`）+ 请求序号
- [ ] 接收端由 `ViewTransform` 推导取样矩形，缩放/拖动**停止后去抖 100–200ms** 才发请求，拖动过程中不刷爆控制通道
- [ ] **零重配路径**：`SameResolution` 档下切换取样矩形时，编解码器不重建、无关键帧风暴、无黑屏，切换期间帧率与端到端延迟无可感知劣化（有实测数据）
- [ ] **2× 原生档免费达成**：编码尺寸取源屏的一半时，2× 放大恰好使取样矩形与编码尺寸 1:1（零缩放、零上采样）；用数学验证 + 实机小字可读性对比 `FullScreen` 模式
- [ ] **冻结画面**：接收端提供冻结按钮，冻结期间本地保留当前帧继续显示并明确标示"已冻结"；它是唯一允许重配编码尺寸的窗口
- [ ] **冻结时重配**：`Native1to1` 档请求仅在被冻结时接受，发送端重配到对应编码尺寸并在完成后恢复实时；重配期间接收端持续显示冻结帧，不黑屏
- [ ] **禁止播放中重配（防回归）**：重配入口有状态机守卫，未冻结时收到 `Native1to1` 请求必须以 `SameResolution` 回应并在 UI 说明；该守卫有单测覆盖
- [ ] 回落策略：ROI 请求超时/连续失败 → 回落整屏取样并在 UI 说明原因；接收端退出放大、断开、切换设备 → 发送端恢复整屏取样
- [ ] 码率：`SameResolution` 档下不做分辨率级调整，但 `BitratePolicy` 需按"每源像素比特"理解取样变化（与切片 12 协同），取样切换不产生码率震荡
- [ ] 坐标映射：ROI + 缩放状态下反向控制仍点得准（逆变换覆盖视图变换与取样矩形两级映射；若切片 11 尚未交付，则在 11 交付时回归验证并在本工单留下待验证标记）
- [ ] 纯逻辑单测：倍率 + 平移 → 取样矩形（含边界钳制、16 倍数对齐、最小尺寸、极窄长条）、2× 时 1:1 成立的数学验证、去抖逻辑、冻结状态机与"禁止播放中重配"守卫、坐标变换往返一致性（用可控时钟推进，禁止真实 sleep）
- [ ] 手工验收：连续捏合缩放/拖动看手机上的小字，2× 时清晰且全程不卡不黑；冻结后放大 4× 能见原生 1:1 像素；解冻后恢复实时
