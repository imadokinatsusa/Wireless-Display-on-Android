# 规格：WhaleCast —— Android ↔ Android 局域网双向投屏

状态：`ready-for-agent`
Slug：`android-cast`
词汇表：见 `CONTEXT.md`

---

## Problem Statement

主人手上有手机、平板、电视盒子等多台 Android 设备，想把其中一台的屏幕（含声音）实时投到另一台上，还想反过来用另一台设备去操作手机；市面上的方案要么依赖厂商生态、要么要求 PC 中转、要么在局域网里裸奔毫无隐私保护，还不给开发者自己调画质和延迟的空间。

具体痛点：

1. **没有 PC 也能投屏**：现有开源方案大多以 PC / 浏览器为接收端，纯 Android ↔ Android 的自建方案极少。
2. **延迟不可控**：走通用投屏协议（Miracast/DLNA）时无法按自己的延迟预算调整码率与缓冲。
3. **声音不同步**：只投画面不投系统声音，或音画偏差上百毫秒，看视频体验崩坏。
4. **只能看不能动**：接收端无法反向操作发送端，投屏只能当"看板"。
5. **隐私无保障**：屏幕内容与输入事件在局域网上明文传输，同一 Wi-Fi 下任何人可嗅探甚至注入。
6. **多设备无余地**：一一写死的架构，将来想一推多 / 多收一必须重写协议。

## Solution

一个可自控的投屏应用：**单 APK、双角色**（发送端 / 接收端，可在同一台设备上切换），在同一个局域网内自动发现设备，用 PIN 或二维码完成配对并全链路加密，之后：

- 发送端用 MediaProjection 抓屏、MediaCodec 硬件编码 H.264，连同系统音频一起推流；
- 接收端硬解渲染到全屏，并按需回传触摸/按键事件，让发送端通过无障碍服务注入真实输入；
- 运行时在界面上暴露码率、延迟、丢包，由码率策略自动调节以守住延迟预算；
- 同一套编码管线顺带支持本地录制 MP4 与截图。

架构上把**唯一的跨端接缝**收敛到 `Transport`，媒体另有 `VideoSource` / `VideoSink` 两个端内接缝；切包重组、握手状态机、码率策略、加密封装全部是无 Android 依赖的纯逻辑，能在 JVM 上单测；采集、编解码、注入、渲染都是接缝背后的适配器。一推多 / 多收一不在 v1 实现，但 `SessionId` 与通道结构预留余地。

## User Stories

### 设备与连接
1. 作为发送端用户，我想要 app 自动列出同一局域网内可接收投屏的设备，以便不用手输 IP。
2. 作为发送端用户，我想要在自动发现失败时手动输入 `IP:端口` 直连，以便在不支持 mDNS 的网络里也能用。
3. 作为两个设备的用户，我想要首次连接时看到 6 位 PIN 并在一端确认，以便确认对面确实是我面前这台设备。
4. 作为用户，我想要扫码完成配对，以便不用读数字、点确认这么多步骤。
5. 作为用户，我想要配对过的设备被记住并免 PIN 重连，以便第二次使用是一键的。
6. 作为用户，我想要在锁屏、切后台、Wi-Fi 抖动、对端退出时看到明确的状态与可恢复的提示，以便知道现在是"断了"还是"在重连"。

### 投屏与质量
7. 作为发送端用户，我想要选择投屏的分辨率与帧率上限，以便在画质与流畅度之间取舍。
8. 作为发送端用户，我想要投屏时看到实时码率、帧率、端到端延迟与丢包率，以便判断当前网络能不能用。
9. 作为接收端用户，我想要在 1080p@60 的局域网环境下把端到端延迟控制在 150ms 以内，以便投屏打游戏不至于无法操作。
10. 作为接收端用户，我想要画面在网络抖动时优先保延迟、允许短暂糊化或丢帧，以便不会越看越延迟。
11. 作为接收端用户，我想要在丢包导致画面花屏时自动向发送端请求关键帧并迅速恢复，以便不用手动重连。
12. 作为接收端用户，我想要投屏过程中音频与画面偏差小于 50ms，以便看视频不出戏。
13. 作为发送端用户，我想要在接收端性能不足时自动降分辨率/码率而不是卡死，以便弱设备也能看。
14. 作为接收端用户，我想要全屏、可缩放、可保持屏幕常亮的观看界面，以便当监视器或副屏用。

### 控制
15. 作为接收端用户，我想要用触摸手势操作发送端屏幕（点按、长按、滑动、双指缩放），以便不用走到手机旁边。
16. 作为接收端用户，我想要外接键盘/鼠标的输入也转发到发送端，以便在电视上像用电脑一样操作手机。
17. 作为发送端用户，我想要在开启反向控制前看到明确的授权说明并随时一键切断控制，以便隐私可控。
18. 作为发送端用户，我想要反向控制仅在已配对且加密的会话中可用，以便没人能隔空操纵我的手机。

### 双角色与本地能力
19. 作为同一台设备的用户，我想要在发送端与接收端角色之间一键切换，以便平板和手机互为对方的屏幕。
20. 作为发送端用户，我想要把投屏内容录制成 MP4 存到本地，以便留存演示或游戏录像。
21. 作为发送端用户，我想要在投屏过程中截图并保存，以便快速分享画面。
22. 作为用户，我想要发送端与接收端共享同一套协议与媒体代码，以便升级时两端不会版本错配。
23. 作为开发者，我想要端内核心逻辑（切包、重组、握手、码率决策、加密封装）不依赖 Android SDK，以便在 JVM 上快速单测而不用真机。
24. 作为开发者，我想要会话能被两台模拟器/真机跑通并复现问题，以便定位只在真实链路上出现的故障。

### 安全与隐私
25. 作为用户，我想要握手阶段用 PIN 确认来抵抗中间人攻击，以便同一 Wi-Fi 下的攻击者不能冒充对端。
26. 作为用户，我想要屏幕内容与输入事件在传输中全部加密，以便别人抓包也看不到我的屏幕。
27. 作为用户，我想要在接收端界面上一键断开并清除配对，以便设备转手时不残留信任关系。

### 观看与缩放
28. 作为接收端用户，我想要捏合放大/缩小、拖动平移、双击复位，以便自己决定看哪一块。
29. 作为接收端用户，我想要在适应屏幕、填充、原始比例之间切换，以便画面不变形也不留无谓黑边。
30. 作为接收端用户，我想要放大后发送端只传我正在看的那块、并保持原生像素清晰度，以便看清手机上的小字。
31. 作为接收端用户，我想要进入/退出放大时画面平滑过渡、不黑屏不长时间冻结，以便切换视角不打断观看。
32. 作为接收端用户，我想要在放大状态下反向控制仍然点得准，以便缩放之后还能继续操作。
33. 作为接收端用户，我想要在 ROI 请求失败时自动回到全屏并在界面上看到原因，以便不会莫名卡在模糊或空白状态。

## Implementation Decisions

### 工程形态
- 单 Gradle 工程、单 APK、双角色，Kotlin + Jetpack Compose，minSdk 29（Android 10，`AudioPlaybackCapture` 与 `AccessibilityService.dispatchGesture` 的下限），targetSdk 取当前最新稳定版。
- 模块划分（按"能否脱离 Android 跑"来切，而不是按 UI 页面切）：
  - `:core:protocol` —— 纯 Kotlin/JVM。包格式、消息类型、握手状态机、能力协商、切包重组、加密封装、码率策略、`SessionStats` 计算。**零 Android 依赖**。
  - `:core:transport` —— `Transport` 接缝与实现：进程内环回实现（测试/单机演示）、TCP 可靠通道（v1）、UDP 媒体通道（后续）。接口面在纯 JVM，Android 侧只做 Wi-Fi 锁与网络状态监听。
  - `:core:media` —— 媒体接缝与**纯逻辑**：`VideoSource`/`VideoSink`/`VideoEncoder`/`VideoDecoder` 接口、合成源与记录汇、`MediaClock`、取样矩形数学。真实采集/编解码的 Android 适配器在工单 04/05 落地时放入 `:core:media-android`，以免污染可 JVM 单测的部分。
  - `:core:session` —— 会话编排：发送管线（源 → 编码 → 切包 → 传输）、接收管线（传输 → 解包 → 重组 → 解码 → 汇）、`SessionStats`，以及切片 03 的握手状态机。纯逻辑、可 JVM 单测，是切片 01 端到端验收的所在地。
  - `:core:control` —— `InputEvent` 模型、事件序列化、`InputInjector`（AccessibilityService 适配器）。
  - `:core:discovery` —— `NsdManager` mDNS 发现、手动 IP、二维码/PIN 配对流程编排。
  - `:app` —— Compose UI、角色切换、权限引导、会话界面与状态展示。
- 依赖方向单向：`:app` → 各 `:core:*`；`:core:*` 之间只允许 `protocol` 被依赖，`protocol` 不依赖任何人。

### 传输与协议
- **唯一跨端接缝 `Transport`**：面向上层暴露"建立会话 / 发送消息 / 收到消息 / 连接状态与统计"四个能力，隐藏 Socket、线程、加解密细节。所有跨端逻辑只能穿过它。
- 通道分工：`ReliableChannel` 走 TCP（握手、控制、关键帧请求、状态上报）；`MediaChannel` 走 UDP（视频/音频包），v1 的第一刀允许媒体先跑在 TCP 上以尽快打通端到端，UDP 化是紧接的独立切片。
- 分帧：可靠通道用长度前缀；媒体通道用定长包头（SessionId、帧序号、包序号、包总数、标志位、时间戳、负载长度），包头解析与切包重组是纯函数，必须有单测。
- 编码帧一律按"整帧切片 + 标志位标记 I 帧/帧尾"传输，不做跨帧合并，便于接收端做丢帧决策。
- 早期建立**协议版本协商 + 能力交集**：握手失败时给明确错误，而不是断连。
- `SessionId` + 通道结构预留一推多 / 多收一，v1 只跑一对一（不做多路分发）。

### 媒体管线
- 编码输入链路：`MediaProjection` 虚拟屏（按屏幕物理分辨率采集，`NativeCapture`）→ GL 纹理 → **可替换的取样阶段**（整屏缩放 / ROI 裁剪）→ `MediaCodec` 输入 Surface，零拷贝语义保持到编码器输入。取样阶段是唯一的画质决策点，也是 ROI 高清放大的落地位置。编码器用硬编 H.264（优先 `baseline`/`main`，按设备能力回退），固定 GOP 便于随机接入，配置为 CBR 或 CQ 以适应码率策略。
- 解码异步模式输出到 Surface；接收端在等到 I 帧后起播，非关键帧丢失时走关键帧请求而非无限等待。
- 时间戳统一由 `MediaClock` 产生：采集端 `nanoTime` 映射到 90kHz 媒体时间轴；接收端用同一时间轴做抖动缓冲与音画同步（音频为主时钟，视频向音频对齐）。
- 音频：`AudioPlaybackCapture` 内录 + AAC（LC）编码；某些应用禁止被捕获时，明确降级为"仅画面"并在 UI 说明。
- 性能预算（`LatencyBudget`，局域网 1080p@60，端到端目标 < 150ms）：采集 ≤ 16ms、编码 ≤ 20ms、网络 ≤ 15ms、抖动缓冲 ≤ 40ms、解码 ≤ 25ms、显示 ≤ 30ms。任何优化都要对照这份预算。
- 本地录制与截图复用同一编码输出（`MediaMuxer` 写 MP4 / `ImageReader` 抓帧），与网络传输互不影响。

### 安全与隐私
- 配对：发送端与接收端首次连接时做临时 ECDH（P-256）密钥协商，用 PIN 或二维码中的共享秘密对协商结果做确认（防中间人），派生 `PairingGrant` 并持久化长期公钥。
- 传输加密：控制面与媒体面统一 AES-128-GCM，按包序号作为 nonce 的一部分防重放；不引入外部 TLS 栈，避免与 UDP 通道的适配成本。
- 反向控制是**受保护能力**：仅当会话已加密且对端已配对时可用；发送端拥有随时撤销开关，UI 必须明确展示"正在被远程控制"。
- 不引入公网中继、不做 NAT 穿透，因此默认只信任局域网；但加密仍必须默认开启。

### 发现与配对流程
- 发现走 `NsdManager`（服务类型 `_whalecast._tcp`），广播设备名、角色、能力摘要；手动 `IP:端口` 作为兜底路径，两条路径汇入同一个连接编排入口。
- 二维码承载设备 ID + 一次性公钥指纹 + 临时端口；PIN 路径由接收端展示 6 位数字、发送端确认。

### 双角色
- 同一 APK 内角色是运行期状态而非编译期分支；一台设备可同时"曾经是发送端"和"现在当接收端"，切换角色必须干净地释放采集/渲染/注入资源。
- 默认角色按设备形态猜测（手机偏发送、平板/电视偏接收），但用户可改并记住偏好。

### 画面缩放与 ROI 高清放大
- 接收端的观看变换由 `ViewTransform`（倍率 + 平移）唯一表达，且必须是**可观察状态**：取样矩形推导与触摸坐标逆变换都只读它，不得从 View 内部状态反推。
- 缩放交互：捏合缩放（倍率有上下限，上限由源屏像素与显示尺寸共同决定）、拖动平移（边界钳制，不留空白）、双击复位、适应/填充/原始比例三种显示模式。
- **清晰度来源是采样策略，不是插值**：发送端虚拟屏始终按屏幕物理分辨率采集（`NativeCapture`），编码前经 OpenGL 取样；**编码输出尺寸取固定档位（16 倍数对齐，通常为源屏的一半）并全程不变**，整屏观看与 ROI 放大只是「取样矩形不同」的两种取值 —— 因此改变倍率与平移**不需要任何编解码器重建**。放大后的清晰度来自"把带宽集中投到小区域"，不是把低分辨率画面拉大——**不接受任何"脑补像素"的方案**。
- `RoiRequest` 走控制通道（可靠、有序、低延迟），携带归一化取样矩形、目标档位（`SameResolution` 零重配 / `Native1to1` 需冻结）、请求序号；接收端在缩放/拖动**停止后去抖**再发，避免连续拖动刷爆控制面。
- 取样矩形做边界钳制与最小尺寸保护（贴边、超界、极窄长条、最小尺寸），边界处理不引入额外等待或重试。
- **绝不在播放中重配编码器**：需要改编码尺寸的档位（`Native1to1`，用于 4× 以上放大仍要原生 1:1 像素）**只允许在接收端「冻结画面」状态下执行** —— 冻结期间接收端本地保留当前帧继续显示并明确标示，发送端从容重配，完成后恢复实时。未冻结时收到 `Native1to1` 请求必须以 `SameResolution` 回应并在 UI 说明原因。重配入口需要状态机守卫与单测，防止未来回归。
- `EncodeResolution` 的档位切换（冻结路径）要走可回落流程：重配失败或超时则保持原档位并恢复实时，不把用户留在冻结或黑屏状态。
- ROI 生命周期与发送端状态绑定：接收端退出放大、断开连接、切换设备时，发送端必须回到 `FullScreen`；请求超时或连续失败自动回落，并把原因上报到 UI。
- ROI 与码率策略协同：区域变小不等于可以无限提码率，`BitratePolicy` 按"每像素比特"重算预算，并在取样切换时不产生码率震荡。
- 坐标换算链固定为唯一一条：接收端视图坐标 → `ViewTransform` 逆变换 → 全屏归一化源屏坐标 →（若处于 ROI 取样，再经取样矩形映射还原）→ `InputEvent`。链路上每一步都是纯函数，必须有往返一致性测试。

## Testing Decisions

**好测试的标准**
- 一个测试失败时必须能指出"哪条行为坏了"，而不是"某个大函数返回不一样了"；断言写在可观察行为上（收到了什么包、渲染了多少帧、状态机到了哪个状态）。
- 只测接缝与纯逻辑，不测 Android 框架内部行为；凡是需要真机才能验证的（编码器输出、虚拟屏、注入生效）放手工验收清单，不做脆弱的自动化。
- 优先手写 Fake（`FakeTransport`、合成画面 `VideoSource`、记录型 `VideoSink`、可控 `MediaClock`），不引入 mock 框架。

**测哪些模块**
- `:core:protocol`（重点，覆盖率最高）：包编解码往返、非法/截断包的拒绝、乱序与丢包下的重组与丢弃策略、握手状态机的全部路径（版本不匹配、能力无交集、超时、对端断开）、加密往返与 nonce 重放拒绝、码率策略在喂入模拟 `SessionStats` 时的决策。
- `:core:transport`：TCP 实现用 localhost 起真实 socket 做集成测试（分帧粘包、半包、连接中断、心跳超时）；进程内环回实现用于会话级测试。
- `:core:discovery`（纯逻辑部分）：配对流程编排、PIN 确认失败路径、免 PIN 重连的信任判断。
- **ROI 与坐标映射**的纯逻辑（放在 `:core:protocol` / `:core:media` 的无 Android 依赖部分）：归一化矩形与编码尺寸的对齐与边界钳制、缩放去抖、`ViewTransform` 逆变换与 ROI 映射的往返一致性——全部用可控时钟推进，禁止真实 sleep。
- `:core:media`、`:core:control`：Android 适配层只做少量 instrumentation 冒烟（编码器能建起来并吐出首个 I 帧、解码器能吃进伪造的 I 帧、`InputInjector` 在授权后能注入一次点击），其余靠手工端到端验收。

**测试先例（本仓库由第一批切片建立，后续照抄）**
- 测试框架：`kotlin.test` + JUnit4（Android 默认），JVM 模块直接跑 `test`，Android 模块用 Robolectric/instrumentation 仅在必要时。
- 目录约定：纯逻辑模块的测试与被测代码同模块同包；测试命名"行为_条件_期望"，中文注释说明意图。
- 时间与并发：所有涉及时间/线程的逻辑必须能注入 `Clock` 与调度器，测试里用可控时钟推动，禁止 `Thread.sleep` 等真实时间。
- 集成测试用 localhost socket，端口 `0` 由系统分配，禁止硬编码端口。

## Out of Scope

- **PC / 浏览器 / iOS / macOS 接收端**（主人明确说 v1 只做 Android ↔ Android）。
- **跨公网投屏**：不做中继服务器、不做 NAT 穿透、不做打洞。
- **一推多 / 多收一的实际分发**：只保留 `SessionId` 与通道结构余地，不实现多路编码与合流。
- **兼容标准投屏协议**：不实现 Miracast / DLNA / AirPlay / Google Cast 的任何一侧。
- **DRM 与受保护内容**：Netflix 等会黑屏，接受该限制，不做绕过。
- **4K / HDR / 多路音轨 / 自定义码流格式**（H.265 也不在 v1，先 H.264）。
- **剪贴板同步、文件互传、通知同步、通话音频转发**。
- **从相机/麦克风投屏**（v1 只做屏幕 + 系统内录音频）。
- **root 方案与系统级权限**：只用公开 API（MediaProjection、AccessibilityService）。
- **账号体系与云同步**：全部本地。
- **AI 超分 / 细节脑补**：不做任何"猜像素"的放大方案，ROI 高清只做真实像素的重分配。
- **多 ROI 并行编码**（画中画同时看两块区域）与 **ROI 下的录制**（本地录制始终录全屏，不受观看缩放影响）。

## Further Notes

**尚未定死、留给后续决策的雾（未升格为工单）**
- 视频包是否需要 FEC（前向纠错）以抗突发丢包；先靠关键帧请求 + 丢帧，实测后再定。
- 是否需要引入 WebRTC 作为 `Transport` 的第二个实现（拿拥塞控制与 NACK/FEC 现成收益）——架构已留位，等自建协议实测数据出来再决策。
- 音频编码选 AAC 还是 Opus（Opus 延迟更低但 Android 硬编支持参差）。
- 一推多的分发形态：发送端多次编码 vs 单编码多路复用（后者更省电，但需要包内分层）。
- 电视端 `AccessibilityService` 可用性差异大，反向控制在电视上的体验需要实测后再定降级策略。
- **「全屏空间分辨率 vs 放大细节」的档位取舍**：单编码器 + 零重配路径下，`EncodeResolution` 的档位同时决定全屏空间分辨率上限与「免费 1:1 档」的位置（免 1:1 倍率 = 源屏尺寸 / 编码尺寸），且带宽总量有限、档位越大每像素比特越少。打破取舍的三条备选路：① **双编码流**（全屏流 + ROI 流并行，切换零重配，代价是并发硬编实例、功耗发热与带宽）→ **已升格为备选工单 16**；② **可伸缩编码 spatial SVC**（一个码流多层，接收端选层解码，最优雅但 Android 硬编支持参差，H.264 基本没有）；③ **高码率硬扛**（档位取源屏 + 30–50 Mbps，Wi-Fi 6 局域网可行，但对路由器负载与干扰敏感）。**判据**：先按单流 + 冻结重配实测；若动态场景（视频/游戏）下放大清晰度不达标，再评估双编码流。
- **并发硬编实例能力**：双编码流方案依赖 SoC 能同时开几个编码会话（低端机型常见 2 个上限），需要在设备能力探测里通过 `MediaCodecList` 查清并把结果记录进能力摘要。

**已知风险**
- `MediaProjection` 在较新 Android 上每次会话都要用户确认，无法静默启动；UI 必须把"确认 → 投屏中"做成顺畅流程。
- `AudioPlaybackCapture` 对声明禁止捕获的应用无效，需要优雅降级与文案说明。
- 部分设备的 H.264 硬编不支持高码率或 `main` profile，需按 `MediaCodecInfo` 能力回退并记录。
- Wi-Fi 省电策略与信道拥塞会让 UDP 抖动剧烈，`JitterBuffer` 需要自适应目标延迟。
- 反向控制的注入依赖无障碍服务常驻，系统可能在低内存时回收，需要状态检测与重新引导。

**性能与验收基线**
- 目标场景：同一 Wi-Fi 5/6 路由器，1080p@60fps，码率 8–20 Mbps 自适应，端到端延迟 < 150ms（争取 < 100ms），音画偏差 < 50ms，控制往返 < 50ms，20 分钟连续投屏无累积延迟增长（这是 TCP 队头阻塞最典型的病症，切片 07 必须验证）。
